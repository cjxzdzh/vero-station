## jadx 会把常量搞反

jadx 把 `String.valueOf(i)` 保留为 `String.valueOf(i)`，读者容易以为 i 就是
线上字节。真实链路：

```
smali const/16 v3, 0x36        →  jadx 显示 T0(54)
smali String.valueOf(I)         →  十进制格式化
0x36 → "54" → 线上字节 0x54
```

两个分析组给出相反答案（一组说 0x36，一组说 0x54）。**判定方法**：各自算 CRC，
发现两者 CRC 都自洽 —— 说明它们说的是两个不同的命令，不是同一个算错。
最终以 smali 的格式化指令为准。

## 并行 agent 会冲突，必须裁决

四组并行查遥测时出现过：

| 组 | 结论 |
|---|---|
| A | `T0(54)` → `A55A08B03D36C5A1` |
| D | `54` → `A55A08B03D5421ED` |

**不能投票，要计算。** 两组 CRC 均自洽 → 两者在说不同的命令 → 去查 smali 的
格式化指令 → 判定 A 组把 smali 常量当成了线上字节。

另一组 agent 自己也犯过错：它引用 smali 的 `const/16 v15, 0x34` 作为线上字节，
但那也是格式化前的整数。

## 我自己的模拟器无法证伪我

这是最贵的教训。

我按「设备推一批就停、主机需每 7 帧索取」的错误理解改了模拟器（改成批处理
模式），然后用它验证同一个错误理解 —— **全绿**。真机一测，遥测完全消失。

用自己写的模拟器验证自己写的协议，等于没验证。

修正后的做法：模拟器必须按**已独立证实的**行为写（本例是常驻流 + 5-slot 结构），
而不是按我当前的假设写。

## 被证伪的假设

| 假设 | 实测否证方式 | 真相 |
|---|---|---|
| 遥测通道是压力 | 用户按压 → 峰值变化，且 App 内部有 `phaseRadians` 式位置量化 | **5 段位置传感器** |
| 「52 是遥测命令」 | 发出后无数据 | **`0x54` 才是**；`0x52` 是运动模式 |
| 每 7 帧续发 command 52 | 20 Hz 下等于每 350 ms 重置流，遥测消失 | **只补发一次** |
| 「33 Hz = 30 ms 连接间隔上限」 | btmon 实测本机间隔是 **50 ms**，而 50 ms 下不可能超 20 Hz | **固件 100 Hz × 3 采样/帧** |
| byte 2 是长度 | App 侧从不校验长度 | **是 cmdId** |
| 逐字节读载荷 | 固定常量 `0x0A`/`0x0D` 落到高位 | **16 位小端 & 0x0FFF** |
| 「100% ≥ 16.61 V」 | 那是曲线最高点，非显示门槛 | **≥ 16.24 V**（96–100 压成 100%）|
| 「按住 70 秒读数无变化」 | 用的是旧解码模型 | 结论无效 |
| 「100% 行程不掉线」 | 观察发生在 Windows，而 Windows 本就不断 | 不构成 Linux 证据 |

## 反复踩的两类 bug

### 1. 字段名不匹配

前端读的字段后端从不发送，`?? "—"` 兜底成破折号，**看起来像没数据**。

```js
s.primary ?? "—"      // 后端字段叫 pressure
```

已加测试：逐个断言前端读的每个字段都存在于 API 响应中。

### 2. 空 catch

```js
} catch(e){}          // 吞掉一切
```

至少掩盖了三个真 bug。现在所有 catch 显示可见信息，且有测试断言
「面板出错」字样存在。

## 十进制/十六进制

Java 里 `String.valueOf(int)` 是**十进制**，但生成的字符串随后按**十六进制**
被解析成字节：

| 传入整数 | `valueOf` | 线上字节 |
|---|---|---|
| `0x36` (54) | `"54"` | `0x54` |
| `52` | `"52"` | `0x52` |
| `0x52` (82) | `"82"` | `0x82` |

搞混这层会选错命令，且**帧结构完全合法、CRC 完全正确**，不会有任何报错。

## 无硬件时能做什么

没有真机时，能做且应该做的：

1. **加可观测性**，让下一次真机测试能直接判因 —— 例如把「设备推了多少帧」
   变成面板上可见的数字
2. **只做能验证的改动**，把不确定的部分留成诊断字段而非猜测
3. **让假设可证伪**：例如「`arm_sensors` 返回实测结果而非无条件 True」
4. **写交叉验证测试**，多个来源冲突时以计算裁决

不能做的：改协议常数、删功能、调阈值 —— 这些都会把「不知道」变成
「看起来能用但错了」。

## 判决实验的设计

Linux 40 秒断链 vs Windows 稳定，用的是**同一份代码、同一台设备、同一套 API**，
唯一变量是主机。这一条就排除了设备、协议、流量、心跳、信号和本软件。

关键在于：**只改一个变量。** 之前的多轮尝试（改配置、换 USB 口、停 HA）
都同时改变了多个条件，因此无法归因。
