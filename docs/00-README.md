## 证据强度标记

- **【源码】** 逐字读过 decompiled 代码，附文件路径与行号
- **【smali】** 读原始字节码。**jadx 常把常量搞错，字节常量以此为准**
- **【实测】** 在真机上量到的数字
- **【反推】** 从实测数据倒推出的结论，未经源码或硬件直接确认
- **【未证实】** 尚未验证，仅记录

## 三条已知的坑

这三条曾让我把功能做错，各自花了一整轮才定位：

1. **十进制/十六进制混淆**。`String.valueOf(0x36)` 得到 `"54"`，所以线上字节是
   `0x54` 而不是 `0x36`。见 [01-protocol.md](01-protocol.md#遥测命令)。

2. **读字节 vs 读 16 位字**。载荷每 4 个 hex 字符是一个 16 位小端字再 `& 0x0FFF`，
   不是逐字节。单字节读法会让 `0x0A` 变成 +2560、`0x0D` 变成 +3328。
   见 [02-telemetry.md](02-telemetry.md#值怎么读)。

3. **byte 2 是 cmdId 不是长度**。我曾硬卡 `length == 41`，那会丢掉其他长度的帧。
   见 [01-protocol.md](01-protocol.md#帧结构)。

### 与 `analysis/` 的关系

`../analysis/` 里有 12 份过程笔记（连同目录页 `00-INDEX.md` 共 13 个 .md），
**它们互相矛盾，只有 4 份完全准确**。实际状态：2 份结论被实测推翻、
2 份部分过时、1 份内部自相矛盾、3 份中期快照或已被取代、**4 份准确**。
每份顶部都加了 `> **状态：...**` 说明它还成不成立。
权威结论只在 `docs/`。

其中一份特别值得注意：`analysis/FINDINGS-telemetry-preconditions.md`
断言「52 是运动模式、真正的启动命令是 device_info 轮询」。
**该结论已被实测推翻** —— 发出 `0x54` 后遥测立刻跑通（2687 帧 / 33 Hz），
且该 App 的完整命令序列里只有 `K0(52)` 一处模式命令。

它仍然保留在 `analysis/`，因为**记录当时的错误推理比假装没发生过更有价值**。
被证伪的假设完整清单见 [06-reverse-method.md](06-reverse-method.md)。
